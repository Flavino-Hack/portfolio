## Le contexte

Dans le cadre de ma formation en **Réseaux Informatiques & Télécommunications**, j'ai voulu pousser l'expérience de l'auto-hébergement à son maximum : **héberger mon propre assistant IA**, sans dépendre d'OpenAI, d'Anthropic ou de n'importe quel service cloud payant.

L'objectif était triple :

- **Autonomie totale** : aucun appel API externe, tout tourne sur ma machine
- **Confidentialité absolue** : les conversations ne sortent jamais de mon infra
- **Accessibilité** : pouvoir discuter avec l'assistant depuis les apps que j'utilise au quotidien (Telegram et WhatsApp)

Ce projet m'a permis de combiner **trois domaines** que j'affectionne particulièrement : l'**administration système Linux**, la **virtualisation**, et l'**intégration de services via APIs**.

## L'architecture

L'ensemble du système repose sur un flux simple mais robuste :

1. **Un utilisateur** envoie un message depuis Telegram ou WhatsApp
2. **Le gateway OpenClaw** (process Node.js) reçoit la requête et identifie le canal d'origine
3. **Il la transmet à Ollama**, qui exécute le modèle `phi3:mini` en local sur CPU
4. **La réponse** est renvoyée à l'utilisateur par le même canal

Tout est hébergé sur une **VM Ubuntu Server 24.04 LTS** virtualisée sous VMware Workstation Pro. Les ports `18789` (gateway) et `11434` (Ollama) ne sont **jamais exposés publiquement** : l'accès au dashboard passe par un **tunnel SSH chiffré**.

## Les étapes de réalisation

### 1. Préparation de la VM

Allocation volontairement généreuse côté CPU (24 cœurs) mais modeste côté RAM (6 Go), car le modèle `phi3:mini` tient largement dans 3 Go une fois chargé.

### 2. Installation de la stack

Deux composants majeurs :

- **Node.js 22.x** : nécessaire pour faire tourner OpenClaw
- **OpenClaw** : CLI installée globalement via npm

```bash
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt install -y nodejs
sudo npm install -g openclaw@latest
```

### 3. Ollama + phi3:mini

Le choix du modèle s'est fait après plusieurs tests :

| Modèle | Taille | Vitesse CPU | RAM |
|---|---|---|---|
| **Mistral 7B** | 4.1 Go | 11 tokens/s | 5 Go |
| **phi3:mini** | 2.2 Go | **24 tokens/s** | 2.5 Go |

`phi3:mini` offre le **meilleur compromis** vitesse/mémoire pour un environnement sans GPU. Le `OLLAMA_KEEP_ALIVE` a été configuré à 10 minutes pour éviter le rechargement du modèle entre deux requêtes (qui prend ~3 secondes).

### 4. Configuration du gateway OpenClaw

Le gateway a été configuré en **mode local strict** :

- Aucun accès depuis l'extérieur
- Authentification désactivée (l'accès est de toute façon restreint par le tunnel SSH)
- Whitelist d'utilisateurs pour Telegram

### 5. Intégration Telegram

Création du bot `@flavien_ai_bot` via **BotFather**, puis configuration du token et de la whitelist :

```bash
openclaw config set channels.telegram.botToken "TOKEN"
openclaw config set channels.telegram.enabled true
openclaw pairing approve telegram RDP2NSTB
```

Le mécanisme de **pairing** est un vrai plus côté sécurité : même si le token du bot fuitait, un utilisateur inconnu devrait être approuvé manuellement avant de pouvoir interagir.

### 6. Intégration WhatsApp

Plus délicate. WhatsApp ne propose pas d'API officielle gratuite pour un compte personnel, donc j'ai utilisé un **plugin communautaire** (via ClawHub) qui fait le pont avec WhatsApp Web :

```bash
openclaw channels add
# Sélectionner WhatsApp (QR link)
# Scanner le QR code depuis le téléphone
openclaw config set plugins.allow '["whatsapp"]'
```

Le plugin maintient une session persistante, ce qui permet de recevoir les messages sans avoir à rescanner à chaque redémarrage.

## Les défis rencontrés

Ce projet a été un vrai terrain d'apprentissage — beaucoup de choses ne se passent pas comme prévu la première fois.

### 🔐 Pas d'accès GPU depuis la VM

**Problème** : ma RTX 4060 n'était pas accessible dans VMware (limitation de la virtualisation GPU sur Windows).

**Solution** : j'ai dû abandonner les modèles lourds (Mistral 7B, Llama 3.1 8B) et choisir un modèle **optimisé CPU**. `phi3:mini` a été le meilleur candidat.

### 📦 Erreur de permission npm

**Problème** : `npm install -g openclaw` renvoyait `EACCES: permission denied`.

**Solution** : `sudo npm install -g` — pas élégant mais rapide. La vraie solution propre aurait été de configurer un **prefix npm** dans le home (`~/.npm-global`), mais pour un déploiement ponctuel `sudo` suffisait.

### 🔑 Authentification du dashboard cassée

**Problème** : `token_missing` en boucle, impossible de se connecter à `127.0.0.1:18789`.

**Solution** : passage en `gateway.auth.mode none` **combiné à un tunnel SSH**. Le gateway n'étant pas exposé publiquement, l'absence d'auth n'est pas un problème de sécurité dans ce contexte.

### 🐢 Lenteur du modèle initial

**Problème** : Mistral 7B tournait à **11 tokens/s** sur CPU — inutilisable pour du chat interactif.

**Solution** : migration vers `phi3:mini` qui atteint **24 tokens/s**, soit un temps de réponse moyen de **2-3 secondes** — acceptable pour du chat.

## Les compétences démontrées

Ce projet a mobilisé des compétences **transverses** :

- **Administration Linux** : gestion de services systemd, scripts bash, permissions
- **Virtualisation** : configuration VMware, allocation de ressources
- **IA / LLM** : déploiement local, choix de modèles, optimisation CPU
- **Intégration API** : Telegram Bot API, WhatsApp Web, webhooks
- **Sécurité réseau** : tunnel SSH, isolation, gestion de tokens

## Pistes d'amélioration

Plusieurs évolutions sont envisagées :

- **Ajout de skills personnalisés** : météo, rappels, veille technologique
- **Migration vers un modèle plus performant** : `qwen2.5:7b` si la RAM le permet
- **Monitoring** : dashboard de performance, alertes en cas de crash
- **Déploiement continu** : pipeline GitHub Actions pour les mises à jour d'OpenClaw

## Ce que j'en retiens

Ce projet m'a appris **beaucoup plus** que ce que j'imaginais :

1. **La contrainte pousse à l'inventivité** — pas de GPU ? Trouver le modèle qui marche en CPU.
2. **La sécurité se pense en couches** — tunnel SSH + whitelist + isolation réseau = défense en profondeur.
3. **Auto-héberger, c'est choisir ses dépendances** — ici, zéro dépendance aux APIs cloud majeures.
4. **L'observabilité compte** — logs, dashboard, tokens/s : impossible d'optimiser ce qu'on ne mesure pas.

C'est typiquement le genre de projet où **le chemin est aussi important que la destination**.
